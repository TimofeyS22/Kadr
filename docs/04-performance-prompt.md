# Kadr v0.7 — системный промпт: производительность длинных проектов

> Читается перед любой работой над скоростью вместе с `CLAUDE.md`. Написан 2026-10-01.
> Повод — факт от владельца: после загрузки видео общей длиной 4 минуты «сайт начал дико тупить, что-то не прогружалось, всё тормозило».
> Цель — ускорение в разы, подтверждённое числами, а не ощущениями.

| QA-perf | Стенд, регресс-гейты | Как не дать скорости снова упасть? |

## 2. Метод (обязателен)

1. Воспроизвести на эталонном сценарии (раздел 3).
2. Снять базовую линию: числа по каждой метрике.
3. Снять профиль (CPU, long tasks, память) и найти, куда уходит время.
4. Отранжировать гипотезы (раздел 4) по измеренному вкладу.
5. Чинить по одной, после каждой — замер «было/стало».
6. Закрепить перф-тестом (`npm run perf`), чтобы скорость не упала снова.
7. Отчёт владельцу в числах.

Запрещено:
- оптимизировать без замера;
- менять несколько вещей между замерами;
- жертвовать WYSIWYG (превью = экспорт).

## 3. Эталонные сценарии и бюджеты

- **S1 (как у владельца):** 4 ролика по 60 с, 1080p30 H.264 ~8 Мбит/с + AAC (≈240 МБ). Импорт → миниатюры и волны → скраббинг → 20 с воспроизведения → открытие листов.
- **S2 (стресс):** один ролик 15 мин 1080p.
- **Условия:** Chromium headless с замедлением CPU ×4 (≈ средний телефон) + функциональная проверка в WebKit.

| Метрика | Бюджет |
|---|---|
| Клипы видны на таймлайне после выбора файлов | ≤ 2 с (копирование в хранилище продолжается в фоне) |
| Суммарное блокирование главного потока (TBT) за S1 | ≤ 300 мс, ни одной задачи > 200 мс |
| Память JS после импорта S1 | ≤ 150 МБ; рост за 60 с воспроизведения ≤ 20 МБ |
| Кадр после перемотки (p95) | ≤ 150 мс |
| Воспроизведение | ≥ 29 кадров/с, пропуски ≤ 3% |
| Тап → лист открыт | ≤ 100 мс |
| Кадр таймлайна при зуме и прокрутке | ≤ 16 мс |
| Экспорт 1080p30 | не медленнее, чем до изменений |

## 4. Гипотезы из чтения кода (подтверждать замером)

| # | Гипотеза | Как проверить |
|---|---|---|
| H1 | Если IndexedDB отказался хранить Blob (Safari), файл собирается из кусков целиком в память: сотни МБ на ролик | heap после `getBlob`; путь `c:` в хранилище |
| H2 | Миниатюры: до 40 декодирований с seek на ролик, в главном потоке, для всех роликов сразу | long tasks при импорте |
| H3 | Волновые формы: декодирование всего звука ролика в главном потоке | long tasks, CPU-профиль |
| H4 | Кадр превью идёт через промежуточный canvas (копия на CPU) перед загрузкой в текстуру | профиль кадра |
| H5 | Звук: отдельный `AudioBufferSourceNode` на каждый AAC-фрейм (~47/с на клип), ссылки копятся | число узлов, heap за 60 с |
| H6 | React перерисовывает крупные компоненты при каждом обновлении `time` | React profiler, TBT во время воспроизведения |
| H7 | Холсты клипов (до 4096 px) перерисовываются на каждом шаге зума | кадр таймлайна при зуме |
| H8 | Пересчёты по всему проекту (ducking, VAD) на каждую правку | профиль правки |
| H9 | Слишком много одновременных декодеров (на iPhone аппаратных декодеров мало) | число открытых `VideoDecoder` |
| H10 | Импорт блокирует работу, пока файл копируется | время до появления клипа |

## 5. Целевая архитектура

1. **Главный поток — только интерфейс и компоновка.** Всё декодирование для анализа (миниатюры, волны, биты, VAD) — в Media Worker (WebCodecs + OffscreenCanvas) с очередью приоритетов: сначала видимые клипы, отменяемо.
2. **Потоково, без файла в памяти.** Хранилище отдаёт дисковый `File`/`Blob`. Если IndexedDB не принимает Blob — OPFS через `SyncAccessHandle` в воркере, а не куски в памяти.
3. **Виртуальный таймлайн.** Рисуются только видимые плитки (плюс запас). Во время жеста зум делается CSS-трансформом, перерисовка — по окончании.
4. **Кэши с бюджетом.** LRU по байтам для миниатюр, кадров и декодеров, ограниченное число активных декодеров, предзагрузка следующего клипа у стыка.
5. **Короткий путь кадра.** `VideoFrame` загружается прямо в текстуру, без промежуточного canvas.
6. **React без лишних перерисовок.** Зависящее от времени — в листовых компонентах; плейхед двигается напрямую через DOM; обновления стора для UI ≤ 30 Гц.
7. **Прогрессивный импорт.** Клип появляется сразу; копирование и анализ идут в фоне с индикатором; редактирование не блокируется.
8. **Наблюдаемость.**
   - Модуль `perf`: метки, long tasks, статистика кадров, память.
   - Оверлей `?perf`: владелец может открыть его на телефоне и прислать числа (FPS, пропуски, память).

## 8. Pre-mortem

| Как провалимся | Защита |
|---|---|
| Headless-замер ≠ телефон | Замедление CPU ×4 + оверлей `?perf` для замера у владельца |
| WebCodecs или OffscreenCanvas в воркере не везде | Проверка поддержки и откат на главный поток с той же очередью приоритетов |
| OPFS в Safari ведёт себя иначе | `SyncAccessHandle` только в воркере; тест записи и чтения; прежний путь через IndexedDB как запасной |
| Оптимизация ломает функции | Полный e2e после каждого блока |
