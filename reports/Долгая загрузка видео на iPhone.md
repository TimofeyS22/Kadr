# Долгая загрузка и потеря качества видео на iPhone

> 2026-10-17. Вопрос владельца: можно ли исправить долгую загрузку видео и потерю качества, есть ли обходные пути, решает ли это Concat.
> Метод: исходный код WebKit, документация Apple, замеры в симуляторе iPhone 17 Pro Max (iOS 26.1) со своей тестовой страницей.
> Уровни источников — по `CLAUDE.md` студии: A — первичные, B — данные с методологией, C — сигналы.

## BLUF (исправлено 2026-10-17, после контрольного замера)

**Обходной путь в вебе есть, и он простой.** В окне выбора фото iPhone один раз выберите «⋯» → «Параметры» → «Формат: Текущий». После этого видео HEVC приходит в Kadr оригиналом за ≈ 3 с, а не перекодированным за 30–90 с. iPhone запоминает выбор. Уверенность высокая для симулятора iOS 26.1; на устройстве не проверено.

| HEVC 4K, 20 с, `accept="video/*"` (как в Kadr) | Что пришло | Время |
|---|---|---|
| Формат «Автоматически» (по умолчанию) | H.264, перекодировано (SHA-256 другой) | 30–93 с |
| Формат «Текущий» | **оригинал** (SHA-256 совпал с исходником), HEVC 4K | **≈ 3 с** |
| «Текущий», следующий выбор без захода в «Параметры» | оригинал | ≈ 3 с — выбор запомнен |

**Первая версия этого отчёта ошибалась** («в вебе не исправить»). Вывод сделали по коду WebKit и замерам с форматом «Автоматически». Режим, который задаёт WebKit, человек может переопределить в самом пикере. Эту ошибку повторил и совет `0058773` в Kadr. Совет исправлен в v1.2.2.

- Видео **H.264** приходит оригиналом за 2 с при любом формате.
- **Через «Файлы»** видео тоже приходит оригиналом: в WebKit этот путь не перекодирует (код, A).
- Собственный импорт Kadr быстрый: 0,45 с до клипов на таймлайне (замер v0.7, 240 МБ).

**Приложение для iPhone** (Capacitor + PHPicker `.current`) остаётся полным решением: оригинал без настройки и «Поделиться → Kadr» из «Фото». Но теперь это не срочно, потому что веб-обход есть.

**Следующий шаг:** проверить на реальном iPhone, что «Текущий» работает и запоминается, — это делает владелец, 2 минуты.

## 1. Почему так: исходный код WebKit (A)

Источник — `Source/WebKit/UIProcess/ios/forms/WKFileUploadPanel.mm`, ветка `main` на 2026-10-17.

| Место в коде | Что делает |
|---|---|
| `_preferredAssetRepresentationMode` | Выбирает режим пикера «Фото». Почти всегда это `Compatible`: в нём «Фото» сами переводят HEVC в H.264. `Current` (оригинал) — только если браузер просит исходный формат картинок и `accept` содержит `image/*` |
| `picker:didFinishPicking:` | В режиме `Current` видео всё равно уходит в `_uploadMediaItemsTranscodingVideo` |
| `WKFileUploadMediaTranscoder` | Перекодирует через `AVAssetExportSession`, пресет `HighestQuality`, в QuickTime |
| Почему «Текущий» помогает | WebKit настраивает пикер в `Compatible` и перекодирует только при `Current` в своей конфигурации. Если человек выбирает «Текущий» в «Параметрах», «Фото» отдают оригинал, а WebKit, видя в конфигурации `Compatible`, файл не трогает (вывод из кода + замер) |
| Комментарий `FIXME (270470)` | Разработчики WebKit сами записали, что режим должен зависеть от `accept`. Баг 270470 открыт с 2024-03-04 и касается только картинок |

Документация Apple по `PHPickerConfiguration.AssetRepresentationMode` (A): режим `.compatible` может перекодировать ассет, `.current` отдаёт его как есть. Приложению доступны оба режима, сайту — нет.

Сигналы (C): на форумах Apple разработчики годами спрашивают, как отключить сжатие видео при загрузке из Safari (например, тред 731042). Рабочего ответа для веба там нет.

## 2. Замеры в симуляторе (ФАКТ, 2026-10-17)

Стенд — тестовая страница с четырьмя вариантами `<input type=file>`; сервер записывает полученный файл, затем сверяются кодек и SHA-256 с оригиналом. Время — от подтверждения выбора до прихода файла (localhost).

| Видео | `accept` | Что пришло | Время |
|---|---|---|---|
| H.264 1080p, 20 с, 34 МБ | `video/*` | оригинал, хеш совпал | 2 с |
| H.264 1080p | `image/*,video/*` + `multiple` (как в Kadr) | оригинал, хеш совпал | 2 с |
| HEVC 4K, 20 с, 63 МБ | `video/*` | H.264 4K, 25 Мбит/с, перекодировано | 31 с |
| HEVC 4K | `image/*,video/*` | H.264 4K, перекодировано | ≈ 30 с |

**Что видит человек:** пикер не закрывается, пока идёт перекодирование, а на миниатюре крутится маленький круговой индикатор.

**Что видит страница:**
- `blur` — когда открылся пикер;
- `focus` и `change` — только когда файл готов, через 34 с.

Отдельного сигнала «iOS готовит видео» нет, а страница в это время закрыта пикером. Показать свой прогресс Kadr не может.

**Качество.** Перекодирование подтверждено:
- кодек сменился;
- хеш другой;
- появилась цветовая разметка BT.709, уровни яркости сдвинулись на 1–3 единицы.

Точную потерю на живом видео **не измеряли**: синтетическая таблица (PSNR 22 дБ) показывает в основном сдвиг уровней и не годится как оценка.

**Не проверено на устройстве.** На реальном iPhone кодер аппаратный, и время может отличаться в любую сторону. Механизм тот же: код WebKit общий.

## 3. Concat (проверено по коду в прошлой сессии, 2026-10-17)

- **iPhone:** выбора видео нет совсем («no file picker on this platform yet»), установка только в обход App Store.
- **Android:** видео копируется в папку приложения байт в байт. Качество не теряется, большой файл копируется долго.

Kadr на Android работает так же: перекодирования нет. Решения для iPhone у Concat нет.

## 4a. Дополнительные проверки (2026-10-17, симулятор iOS 26.1)

| Проверка | Результат |
|---|---|
| «Текущий» после перезапуска Safari | Держится: HEVC 4K снова пришёл оригиналом за 1 с |
| HDR-оригинал как с iPhone (HEVC Main 10, HLG, BT.2020) в Kadr | Импорт и превью работают, цвета совпадают с миниатюрой «Фото», картинка не «выцвела». Раньше перекодирование iOS заодно переводило HDR в SDR, теперь Kadr получает HDR как есть |
| Экспорт из HDR-исходника | WebKit на macOS: 3,3 с, без ошибок декодирования (новый e2e). В симуляторе экспорт не завершается ни для какого исходника, даже H.264: там нет аппаратного кодера. Экспорт проверять на телефоне |
| Можно ли узнать, что iOS перекодировал файл | По `lastModified` нельзя: копия несёт дату оригинала. Поэтому совет показывается один раз при первом видео, а не по признаку перекодирования |
| Вставка видео из буфера | Не даёт файла: в WebKit на iOS пути к файлам бывают только при перетаскивании (`PasteboardIOS.mm`, код, A) |
| Перетаскивание из «Фото» в Safari | По коду WebKit не перекодирует: берёт у источника представление максимального качества. На iPhone это жест двумя руками, вживую не проверено. Как основной путь не годится |

Сигналы (C): поддержка Echo360 (обновлено 2026-01-06) советует пользователям тот же переключатель «Формат → Текущий». На форумах Apple (тред 743037) спрашивали, может ли страница сама включить «Текущий». Ответа нет: со страницы это недоступно.

## 5. Рекомендация

1. **Веб (сделано в v1.2.2):** совет при первом видео на iPhone теперь ведёт к «⋯ → Параметры → Формат: Текущий», путь через «Файлы» остаётся запасным. Ключ совета сменил версию, поэтому увидевшие старый (неверный) совет получат новый один раз.
   - Уверенность высокая для симулятора iOS 26.1.
   - Вывод изменится, если на реальном iPhone «Текущий» не запоминается или видео всё равно перекодируется.
2. **Приложение для iPhone** — ставка следующего цикла, если владелец готов к аккаунту Apple.
   - Уверенность средняя: технически решение надёжно, а ценность зависит от доли пользователей iPhone и их жалоб.
   - Самый дешёвый тест — прототип в симуляторе: HEVC 4K из «Фото» приходит в веб-код оригиналом (тот же SHA-256) быстрее 3 с.
   - Kill-критерий: если не приходит, приложение не нужно.
3. **Android:** перекодирования нет. Время копирования больших файлов измерить на телефоне через `?perf`, прежде чем что-то оптимизировать.

**Что нужно от владельца:**
1. На своём iPhone выбрать видео в Kadr через «⋯ → Параметры → Текущий» и сказать, стало ли быстро.
2. Решение по аккаунту Apple Developer ($99/год) теперь не срочное.
